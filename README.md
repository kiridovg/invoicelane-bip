# Invoicelane

Модуль обліку рахунків (invoices).

**Стек:** Laravel 13 / PHP 8.4 / PostgreSQL 18 · Nuxt 4 / Vue 3.5 / TailwindCSS 4 · Docker Compose

---

## Запуск

Потрібен лише Docker.

```bash
git clone git@github.com:kiridovg/invoicelane-bip.git invoicelane-bip
cd invoicelane-bip
docker compose up -d
```

Перший запуск — 3–5 хвилин (образи, залежності, міграції, сідер).

| | |
|---|---|
| Frontend | http://localhost:3000 |
| API | http://localhost:8000/api/invoices |
| Health-check | http://localhost:8000/up |

База наповнюється десятьма рахунками `INV-2026-0001` … `INV-2026-0010` — з простроченим, з нульовим ПДВ і з усіма трьома статусами.

```bash
docker compose exec api php artisan migrate:fresh --seed   # перезалити дані
docker compose exec db psql -U invoicelane -d invoicelane  # консоль БД
```

### API

| Метод | Шлях | |
|---|---|---|
| `GET` | `/api/invoices` | список; `page`, `per_page`, `status` |
| `GET` | `/api/invoices/{id}` | один рахунок |
| `POST` | `/api/invoices` | створення |
| `PUT` | `/api/invoices/{id}` | оновлення, лише для `pending` |

Коди: `200`, `201`, `404`, `409` (статус не дозволяє редагування), `422`.

## 1. Як структуровано frontend і backend

Монорепозиторій, два незалежні застосунки, спілкування лише по HTTP: `apps/api` (Laravel) і `apps/web` (Nuxt).

Backend — потік в один бік, кожен шар з однією відповідальністю:
`Route → Controller → FormRequest → DTO → Service → Repository → Model → Resource`

- **FormRequest** — уся серверна валідація (окремі класи на створення, оновлення, параметри списку).
- **DTO** — типізований контракт замість наскрізних масивів; HTTP-запит глибше не проникає.
- **Service** — бізнес-правила: розрахунок `gross_amount`, заборона редагування не-`pending`.
- **Repository** — два методи (`paginateLatest`, `persist`), не дзеркало Eloquent.

Frontend: `pages` / `components` / `stores` (Pinia) / `schemas` (zod) / `utils`.

## 2. Які компроміси зроблено

- **Docker без Dockerfile.** Ціна — PHP-розширення ставляться при кожному старті (~30 с) і фронтенд у dev-режимі. Виграш — швидкість для тестового.
- **`gross_amount` не приймається від клієнта.** Єдине джерело розрахунку — сервер. Інваріант із ТЗ 4.2 гарантований конструкцією та CHECK-констрейнтом, а не перевіркою даних, які однаково відкидаються.
- **Суми — рядки, не float.** `decimal(15,2)` у схемі, каст `decimal:2`, `bcmath` для арифметики: у бухгалтерії розбіжність у копійках неприпустима.
- **zod 3, а не 4** — стабільний `@vee-validate/zod` вимагає `zod ^3.24`; підтримка zod 4 є лише у vee-validate v5 beta.
- **TypeScript 5, а не 7** — `vue-tsc` ще не працює з сімкою. Перевірка типів важливіша за версію компілятора.
- **Без Sanctum** — аутентифікація за ТЗ не потрібна. `routes/api.php` створено вручну.

## 3. Що покращив би у production

**За 4–5 годин, які було витрачено, дуже важко втілити всі тонкощі — їх досить багато, і, швидше за все, я не опишу їх усі, бо, чесно кажучи, я вже втомився це робити)**

- **Додати endpoint для зміни статусу інвойсу — у пункті 6 це не передбачено**
- **Обробка DB constraint violations у Сервісі — оскільки це призведе до помилки 500, над обробкою помилок ще потрібно попрацювати в інших випадках**
- **Multi-stage збірка**
- **Оновлення в реальному часі** У завданні обмежився перезапитом при поверненні фокуса на вкладку щоб запуск лишався однією командою без брокера.
- **Feature-тести** на валідацію сум і дат, унікальність номера, `404` і заборону редагування `approved`/`rejected` окремою базою в тому ж Postgres.
- **i18n замість зашитих рядків, rate limiting, структуровані логи з request-id.**
- **Постачальник як окрема сутність**
- **Журнал змін.** Для бухгалтерії критично, хто і коли змінив суму. Зараз є лише `updated_at` без історії.
- **Верхня межа сум.** Число з сімнадцяти цифр проходить валідацію і падає на переповненні `decimal(15,2)` — потрібне правило `max`, прив'язане до точності колонки.
- **Єдиний стиль коду в команді.** Laravel Pint для PHP, ESLint + Prettier для фронтенду, спільний `.editorconfig`, pre-commit хук через lint-staged і та сама перевірка в CI. Без цього діф у пул-реквесті наполовину складається з переформатування, а рев'ю перетворюється на суперечки про пробіли.
- **Статичний аналіз як частина пайплайну.** PHPStan/Larastan для бекенду і `nuxt typecheck` для фронтенду — обидва запускаються в CI, а не «коли хтось згадає». Зараз перевірка типів існує лише як локальна команда.
- **OpenAPI-специфікація як контракт.** Типи `Invoice` на фронтенді зараз написані вручну і дублюють `InvoiceResource` — вони розійдуться при першій же зміні поля. У проді специфікація генерується з коду, а TS-типи — зі специфікації.
- **Версіонування API** (`/api/v1`), щоб зміна формату відповіді не ламала вже випущені клієнти.

## 4. Які UX edge cases враховано

- **Два стани завантаження**: холодний старт показує скелетон, фонове оновлення лишає таблицю на місці й приглушує її.
- **Помилка не ховає дані**: якщо оновлення впало, а список уже є, показується банер «попередні дані» замість повноекранної помилки.
- **Порожній список — не помилка**, окремий стан. Сторінка поза діапазоном (`?page=99`) — теж окремий, із поверненням до першої.
- **`422` розкладається по полях** через `setErrors`, а не в загальний банер.
- **Блокування форми — за `is_editable` з API**, фронтенд не дублює правило `status === 'pending'`.
- **Кнопка пояснює, чому неактивна** — і підказкою, і текстом поруч.
- **Кома як десятковий роздільник** приводиться до крапки прямо в полі.
- **Рядок клікабельний, але номер — справжнє посилання**
- **Прострочення підсвічується лише для `pending`** — для затверджених і відхилених воно не має сенсу.
- **Підсумкова сума на льоту позначена як попередній перегляд**; після збереження форма перезаливається значеннями з сервера.
- **Форма скидається при переході між рахунками**, інакше в полях лишилися б суми попереднього документа.
- **Номер сторінки живе в URL**
